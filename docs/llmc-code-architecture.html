01

The problem we are solving

why this exists

You can download a great model today. You still can't use it to code.

A language model does exactly one thing: you give it text, it gives you text back. That's all. It cannot open a file. It cannot run your tests. It forgets everything the moment it replies.

So when you load a model in LM Studio, you get a chat box. What you actually wanted was something that reads your project, changes your code, runs your tests, sees what broke, and fixes it.

The missing piece

Something has to sit between the model and your computer. It gives the model a way to ask for things, does those things for it, and shows it what happened.

That middle program is called a harness. Building one is what this deck is about.

Why run it on your own machine?

  • Your code stays yours. Nothing is uploaded anywhere.
  • It's free to use. No per-word charges, no limits.
  • It works with no internet. On a plane, in a lab, anywhere.
But running locally changes everything

A cloud tool can assume a huge, fast, well-behaved model. We can't assume any of that. Our model is smaller, slower, and messier. Almost every custom part in this deck exists because of that one difference.

Five things local models force you to build

The difficultyWhat we had to build
Every model asks for things differently 7 different readers for the same request, plus a layer that fixes wrong spellings of the same option name
Long chats get very slow
the model re-reads everything each time		 Context management — keep the conversation small, and re-use the work the server already did
The model can only hold a little text at once Search — store everything, then look up only the few bits this question needs
Laptops get hot Forced breaks and shorter replies, so an hour of work doesn't cook the machine
It changes your real files Ask-before-you-act, undo, and limits on where it can write
In one sentence

We are building the program that turns "a model on your laptop" into "an assistant that gets work done on your laptop."

What you see — and what's kept on your disk

boxes 1 & 9 · top blue, bottom right grey
repl.py
The prompt, the commands, the colours, the status bar.
__main__.py
Command-line flags, and the one-shot mode.
Why is this 4,000 lines?
Because two libraries both want to control the same terminal: one owns typing (history, editing, tab-completion), the other owns colour and layout. Left alone they fight over the cursor, and you get half-drawn prompts and stray characters. Most of that file is keeping them out of each other's way.
Two decisions worth copying
DecisionWhy
Don't print the reply as it arrives — collect it, then print once Printed live, headings and code blocks show up as raw ## and backticks. Collected first, they render properly. The spinner is what moves while you wait.
The status bar reads a cached value, refreshed once per turn It's redrawn on every keystroke. Asking git for the branch name that often would make typing visibly laggy. Expensive work happens once a turn, not once a letter.
And the one that stops it annoying you

A line starting with / is only treated as a command if it's one we actually know. Anything else is sent to the model as ordinary text — so asking about another tool's /deploy command doesn't get hijacked.

config.py
Your settings.
session.py
Past conversations.
checkpoint.py
Undo.
Why a whole box just for saving things?
Because all three have the same failure mode: a crash halfway through writing. Settings, conversations and undo copies are each one file that must be either completely old or completely new — never half-written.
The trick, used identically in all three

Never write to the real file. Write to a temporary file next to it, then rename it over the top. Renaming is a single, indivisible step — so a crash leaves you with either the old file or the new one, and never a broken half of each.

Settings: the rule that stops surprises
Three layers, in order: built-in defaults, then your saved file, then flags you typed just now. Each layer only overrides what it actually mentions.
And a flag you typed is not saved unless you ask for it — so a quick experiment never quietly becomes your permanent setup.
Why this matters more when it's local

The saved conversation contains the contents of files the model read. On a cloud tool that would be a real problem. Here it never leaves the machine — which is exactly the reason people run it locally in the first place.

The brain — decides what to do next

box 2 of 10 · green, centre of the map
agent.py
Runs the loop. Holds the conversation. Decides when to stop.
orchestration.py
Sends a second assistant off to do a job on its own.
prompts.py
The standing instructions that shape how it behaves.
What does each one actually do?
agent.py keeps a plain Python list of messages. Each round it sends that list to the model. If the reply contains a request, it runs it, adds the result to the list, and goes round again. If the reply is just words, that's the answer — stop.
orchestration.py adds one special tool: "start another assistant". That helper gets a fresh, empty conversation and a smaller set of abilities. It reports back in a few lines.
prompts.py holds the instructions for four different jobs — planner, explorer, coder, reviewer — that get pasted at the top of the conversation.
How do the three fit together?
Three separate questions, three separate files:
• prompts.py decides HOW it behaves.
• agent.py decides WHEN to stop.
• orchestration.py decides WHO does the work.
Change one and the other two keep working — which is why the behaviour can be tuned by editing English, with no code change at all.
The rule that makes it testable

The brain never opens a file and never opens a connection. It only ever asks the hands or the mouth. So we can hand it a fake model and a temporary folder and test the entire decision-making layer — which is how 1,355 tests run offline in seconds.

Why does a local model need all this?
A big cloud model mostly gets it right first time. A small local one does not, and the brain is where you absorb that:
What goes wrong locallyWhat the brain does about it
It forgets to look first and answers from imagination prompts.py spells out explore → plan → act → validate, and caps how many files it may read before it must search instead
It loops — asking for the same file over and over agent.py compares each round's requests to the last. Four identical rounds and it stops
It sends a broken request Three rounds where everything failed to parse and it stops. One good request resets the count — progress is progress
It thinks, then says nothing Re-asks up to twice, with the reply length cap lifted
A big job won't fit in its small memory orchestration.py splits it: helpers do the reading, the main conversation only receives conclusions
The shape to copy

Your loop should assume the model will misbehave. Every stop-condition here exists because something actually went wrong once — and each one has a number attached, so it can never argue with you about when to give up.

If file writing lived in three places, you'd have three chances to forget the check.
What every tool must promise
Three rules, no exceptions:
RuleWhy it has to be a rule
Never crashA crash ends the whole turn. A failure message gets read by the model, which then tries something else.
Always cut output shortWhatever a tool returns is added to the conversation and re-sent forever after. One giant result poisons the rest of the session.
Explain the failure"error" makes the model guess. "no such path; did you mean llmcode/agent.py?" gets fixed next round.
Your error messages are now prompts

The most surprising thing about building an agent: the text you put in an error is read by the model and acted on. Write it for the model, not for a log file.

How does a tool actually get used?
Four steps, every time:
#Step
1Its description goes to the model with the conversation — name, purpose, options.
2The model replies asking for it by name, with options filled in.
3We fix the option names (local models get them wrong), ask you if it's dangerous, then run ordinary Python.
4The result is cut short and added to the conversation.
Why it matters more on a local model
A small model gets paths and arguments wrong constantly. So the hands do two extra jobs a cloud harness wouldn't bother with:
  • remediation.py corrects the obvious mistakes and retries, instead of burning a whole round on a typo.
  • The caps are tighter than you would set for a big model — the memory it all has to fit into is much smaller.
And about other people's tools

An mcp.py tool can declare "I'm harmless, don't ask". A bad one could say that about something destructive — so the claim is ignored unless you said you trust that program. Trust is your call, never the tool's.

The mouth — talks to the model

box 4 of 10 · purple, bottom centre
the real one
Sends the conversation to LM Studio and reads the reply back as it arrives.
the translator
Understands 7 ways of asking for things, and turns them all into one shape.
the fake one
A scripted stand-in model, so the tests need no GPU and no internet.
Why is there a box here at all?
Because the rest of the program should never know which model you loaded. Every family has its own quirks; if those leaked into the brain, changing model would mean changing the loop. So this box always emits the same three things:
real model or fake one — both produce only these
{"type":"text",      "text": … a piece of the reply …}
{"type":"tool_call", "name", "arguments": … what it wants done …}
{"type":"done",      # exactly one, always last}
The fiddly bit: replies arrive in pieces
A single request arrives split across dozens of fragments — and if the model asks for two things at once, the fragments are interleaved. We collect them into numbered slots and assemble them only once the reply ends.
They are joined in one go, not glued on one at a time — with a whole file arriving in pieces, that is the difference between instant and painfully slow.
Why the fake model is the best decision in the project
Nearly every bug here is a loop bug: a request with no matching result, a counter that never resets, messages in the wrong order. You cannot chase those against a real model — it answers differently every time, and slowly. Against a script they are ordinary tests that run in milliseconds.
Build this seam on day one

Ten minutes at the start: never call the model directly, always go through a swappable piece. Adding it later, once a dozen places call the model, is miserable.

And the privacy part
Because this is the only place that opens a connection, it is also the only place privacy has to be enforced:
  • The address must be your own machine, pinned to the exact number it resolved to, so it cannot quietly become something else later.
  • Proxy settings are ignored, so traffic meant for your own machine can never be routed out through someone else's server.
  • If any of that can't be guaranteed, it refuses to start.
One box, one responsibility

All of this follows from a single sentence: this is the only code that talks to the outside. The translator, the fake model and the privacy lock are all about that one boundary.

What happens when you press Enter

the main flow
Why it loops

One question and one answer cannot fix a bug. The model has to look, try something, see what happened, then try again. Every time round, it knows more than it did before.

What makes it stop

An answer with no requests in it. If the model just talks, it means it has nothing left to look up — so what it said is the answer, and we stop.

How it stays under control

A hard limit of 80 times round, plus eight more stop-conditions. Anything that writes a file or runs a command asks you first. Just reading? It goes ahead.

08

The whole agent, in 20 lines

the loop

Take away 3,000 lines of safety checks and polish, and this is the whole thing. It is not pseudo-code — this runs, and we tested it with a fake model.

the heart of every coding assistant ever built
def agent(task, max_steps=12):
    messages = [{"role":"system", "content": SYSTEM},
                {"role":"user",   "content": task}]

    for _ in range(max_steps):              # the iteration guard
        reply = client.chat.completions.create(
            model=MODEL, messages=messages, tools=SCHEMA
        ).choices[0].message
        messages.append(reply.model_dump(exclude_none=True))

        if not reply.tool_calls:            # plain words = DONE
            return reply.content

        for call in reply.tool_calls:
            args = json.loads(call.function.arguments)
            if call.function.name in NEEDS_OK and not ask_user():
                out = "DENIED by the user."
            else:
                try:
                    out = TOOLS[call.function.name](**args)
                except Exception as e:      # errors are DATA
                    out = f"ERROR: {type(e).__name__}: {e}"
            messages.append({"role":"tool",
                             "tool_call_id": call.id,
                             "content": str(out)[:4000]})   # ALWAYS cap

    return "Stopped: hit the step limit."

Five small decisions, each a big deal

The lineWhy it has to be there
str(out)[:4000]Tool output is added to the conversation and re-sent forever after. One giant result ruins the rest of the session. So we cut it short right where it is produced.
except → "ERROR: …"If a tool crashes, the whole thing stops. Instead we turn the failure into a message — and the model reads it and tries something else.
range(max_steps)Without a limit, a confused model keeps trying forever. Your laptop runs all night.
NEEDS_OKAnything that could break something asks you first. You stay in charge.
The system promptWe change how it behaves by writing English, not code. Adding "look before you answer" genuinely changes the quality of the result.
The error message is the important one

Compare two ways of reporting the same failure:
• "error" → the model has nothing to go on. It guesses, and keeps guessing wrong.
• "path not found; did you mean llmcode/agent.py?" → fixed on the very next try.
Your error messages are now instructions to the model. Write them for the model to read, not for a log file nobody opens.

Every tool answers the same way

Either {"ok": true, …} or {"ok": false, "error": …} — never a crash. A crash would end your turn. An error just tells the model what went wrong, so it can try something else.

The description is doing real work

Write "Read a file" and the model reads whole files. Write "Read a file — for big ones, ask for a range" and it starts asking for ranges.
Same code underneath. Completely different behaviour.

The eleven tools

Two real bugs this cost us

• Our own docs said writes couldn't escape the project folder. For run_bash that was simply not true. A safety promise that isn't real is worse than no promise, because people relax.
• Writing a file whose contents looked like a tool request corrupted it — the reader got confused about where the file ended.

Custom #1 — every model speaks a different language

providers.py
Why

Cloud models all ask for things the same way. Local models come from a dozen labs, each with its own idea — and many don't use the proper channel at all. They type the request out as ordinary text and hope you notice.

What

A reader that understands seven ways of saying the same thing: one proper format, five that model families made up, and one we invented for models that can do none of them.

How

Spot the style, pull out the name and details, turn it into one plain Python value. The rest of the program only ever sees one shape.

The bug that forced this

Writing files did not work for weeks. Always the same error: "requires a string 'path'".

Two problems stacked up. The model wrote its request in a style we couldn't read yet — and it called the option file_path, because that is what it saw most in training, while our tool called it path.

The genuinely hard part: where does the text stop?

A model will often say "here comes the file content", paste an entire Python file, and then never say where it ended. So we have to guess the end point.

Guess too early and half the file is lost. Guess too late and the next request gets written into the user's source file. That second one actually happened.

Custom #2 — wrong argument names, and refusing to guess

tools.py

Even once we can read the request, the option names are often wrong. Local models learned from other tools' docs, so they use those names — file_path where we say path.

Read that comment in the middle again

This table guesses what the model meant. One obvious-looking guess was deliberately left out, because getting it wrong would overwrite a whole file with a two-line fragment. Knowing which guesses not to make is the whole skill.

The rule that keeps the guessing safe

for canonical, syns in aliases.items():
    cur = args.get(canonical)
    if cur not in (None, ""):
        continue      # model gave a real value — authoritative
    if cur == "":
        continue      # explicit empty — intentional, keep it
    for syn in syns:    # else backfill from the first alias present
        …
  • A guess can only fill in a blank. It can never overrule something the model actually said.
  • "Nothing" is a real answer. Empty content means "make an empty file" — that is an instruction, not a gap to fill.
  • Nothing is touched unless we actually fix something — so what you were shown in the confirmation prompt is exactly what runs.

And two places we deliberately refuse to guess

What happenedWhat we do about it
Two tool-shaped blocks in one replyRun none of them. If we ran only the first, the second would vanish silently and the model would never find out — it would carry on believing both had happened.
A block inside prose or a <think> sectionIgnore it. Otherwise, a model explaining how rm -rf works would actually delete your files.
The rule worth taking away

Be generous about what you try to understand. Be strict about what you actually do.

Misunderstanding costs one wasted turn. Acting on a misunderstanding costs the user's files.

Keeping the chat small — why not just send everything?

box 5 of 10 · orange, top left
First, the thing that makes this necessary
The model has no memory between messages. So every single turn, we send the entire conversation again from the beginning — and it reads all of it before writing one word of the reply.
Imagine a colleague who forgets everything between sentences and has to re-read the whole meeting transcript each time you speak. That is exactly what is happening.
So why not just send it all and let it sort it out?
Three reasons, and only the first is the obvious one:
ReasonWhat actually happens
1. It gets slow Reading time grows with the chat. Typing speed doesn't change — so it just sits in silence for longer and longer before it starts answering.
2. It doesn't fit A local model can only hold so much. Past that point the oldest messages fall off silently — including, quite possibly, the instruction that mattered most.
3. The answers get worse This is the one people miss. Your actual question ends up buried in thousands of lines of stale tool output, and the model starts answering about a file it read six steps ago. More context is not more understanding.
The measurement that started all this

Someone typed "what happened?" — four words. We sent 55,000 words of old conversation with it. The reply took about 20 minutes.

Over half of what we sent was old tool output — files read six steps earlier that nobody needed any more.

So how do we pick just the part that's needed?
Five steps, run in this order at the start of every turn — cheapest first, and each one only does something if the one before wasn't enough:
#StepWhat it decides
1Judge the question Quick question, or real work? "thanks" and "refactor the parser" should not get the same treatment.
2Set a size budget A number for this turn. Small for a quick question, up to 3× for a whole-project job.
3Shorten what's stale Tool results from finished steps get cut to their first few lines, with a note saying how to get the rest back.
4Look up what's relevant Search past conversations for the few bits that match this question, and attach only those. (box 7 — RAG)
5Summarise, if still too big Ask the model to condense the old turns into one short note. This costs a round trip, so it's the last resort.
The rule underneath all five

The most recent exchange is always kept whole. Everything being shortened or summarised is from turns that are already finished. What you just said, and what just happened, is never touched.

Keeping the chat small — how the shortening works

box 5 of 10 · continued
Shortening — free, and it happens every turn

Old tool results get cut to their first few lines. A note is left saying "there was more here — ask again if you need it."

Two details matter. The note explains itself, so the model re-reads the file rather than inventing what was in it. And anything already shortened is left alone next time — otherwise each turn would nibble off another piece until the note ate itself.

Summarising — costs a round trip

When shortening isn't enough, we ask the model to write one short note covering the old turns: decisions made, files touched, what's still to do.

This is not deleting old messages. Deleting is one line of code — and it throws away every decision you made together.

Summarising can backfire — so we check

A small model sometimes writes a summary as long as the thing it summarised.

So we keep a copy first. If it didn't save at least a few percent, we put the original back. A fix that doesn't fix anything still costs you time.

Re-using the server's work — free speed

box 6 of 10 · purple, left side
Why this works

The server remembers the reading it already did. If your next message starts with exactly the same text as the last one, it can skip straight past all of it — which is most of your waiting time, for free.

The industry name for this is prompt caching, or CAG.

What we do

One rule, everywhere in the code: only ever add to the end of the conversation. Never insert in the middle. Never reorder. Never edit what came before.

How the extras fit in

Anything temporary — things we looked up for this question, a hint for this message — is stuck on the very end, and only on the first try. The end was never cached anyway, so it costs nothing.

Both pictures contain the same information

The only difference is where the new note was put. Put it at the end and the server skips almost everything. Put it in the middle and the server has to re-read every word after it — even though none of those words changed.

The same rule shows up three more times

• A message with no picture stays plain text, because attaching one changes its shape.
• The tool descriptions are built once and re-used, so their order can't drift.
• A summary that didn't help gets undone — the code would rather carry extra words than disturb the beginning.

Looking things up — remembering without re-reading

box 7 of 10 · blue, right side
Why

We just said: send less history. But some of it genuinely matters. Drop it and the assistant is forgetful; keep it all and it is slow.

What

Keep everything in a store. Search it with whatever was just asked. Send only the few pieces that matched. The usual name for this is RAG.

How

Two search engines, both written by hand: one for exact words, one for meaning. The results are merged and attached as a single note.

Where it lives

One plain file per project, with the numbers in a second file beside it. The index is built once and re-used — otherwise every search would re-read everything.

Retrieval runs ONCE per turn

Before the loop starts, never inside it. Searching costs time; doing it on every step would undo the speed it was meant to buy. A message like "thanks" skips it completely.

Failure is always swallowed

If the search breaks for any reason, we carry on with nothing. Memory is a bonus. Losing it must never cost you the answer.

Looking things up — how the word search ranks

box 7 of 10 · continued
llmcode/memory.py — the whole scoring loop, nothing hidden
for term in q_terms:
    f = tf.get(term, 0)          # times the term is in THIS doc
    if f == 0: continue
    n_q   = df[term]              # how many docs have it at all
    idf   = math.log(1 + (n - n_q + .5) / (n_q + .5))   # rarity
    denom = f + k1 * (1 - b + b * (dl / avgdl))     # length
    s    += idf * (f * (k1 + 1)) / denom          # saturating

Why not just count how many words match? Because every document contains "the". This formula is the classic fix. It still beats fancier methods on code, where an exact function name matters far more than general vibes. Its proper name is BM25.

Throwing away "the" and "and" is doing real work

It looks like tidying. It isn't. If a question and an old note share only the word "the", the score comes out above zero — and the next slide only reaches for the meaning search when the score is exactly zero.

Removing filler words is what makes "zero" actually mean "nothing in common".

Don't copy a filler-word list off the internet

Ours deliberately keeps on, off, no and not. In a command-line tool those aren't filler — they're values, as in /mcp on.

A list copied from somewhere else would have quietly deleted them, and searches for commands would have stopped working.

Looking things up — searching by meaning

box 7 of 10 · continued
What "searching by meaning" actually is

Every piece of text is turned into a list of 768 numbers. Think of it as a position on a map, where things about the same topic end up near each other.

"where do my settings live?" lands right next to "the config file is in ~/.llmcode" — even though they share not one word.

To compare two of these, we measure the direction they point in, not how far away they are — distance mostly just reflects how wordy the text was. That is 12 lines of code:

llmcode/memory.py — cosine()
dot = na = nb = 0.0
for x, y in zip(a, b):
    dot += x * y      # how much they point the same way
    na  += x * x
    nb  += y * y
if na <= 0.0 or nb <= 0.0: return 0.0
return dot / math.sqrt(na * nb)     # 1.0 = identical meaning
Notice what it promises

It never crashes. Given nonsense it returns zero — which means "no match", and is exactly the right answer. One corrupted note can never take down your whole turn.

The one decision that made this fast

Where meanings are stored — no database needed

box 8 of 10 · purple, right side
Why

Those lists of numbers must survive closing the terminal. The usual answer is a special database — often a whole extra program running in the background. Absurd for a personal tool holding a few thousand items.

What

A plain list in memory, one readable file for the text, and a second file holding just the raw numbers. Searching is an ordinary loop.

How

Each number takes 4 bytes instead of the ~32 an ordinary Python number costs. And saving them as raw bytes avoids turning every single one into text and back again.

When this simple approach is the right one

Thousands of items, one machine, one person. Looping over 4,000 of them takes milliseconds.

You need a real database at millions of items, or when several programs share one index — not before.

The lesson worth keeping

Whenever two files have to agree with each other, one of them must be able to prove it matches. A short fingerprint is the cheapest possible proof.

It is the difference between "rebuild once on next launch" and "quietly wrong answers, forever, with no error".

Custom #10 — helping it find the right code

code_index.py · repo_graph.py
Why

A small model cannot read a 50-file project. Three files already fill it up. It needs to find the right 40 lines, not read everything and hope.

What

A search the model runs itself, using the same two engines as memory — plus a short map of the project so it knows what exists at all.

How

The code is cut up function by function, not every 50 lines — so every result is a whole, complete thing. Built once, re-used, and always cut short before it gets huge.

Three deliberate choices

ChoiceReason
AST-aware chunkingA result that starts halfway through a function teaches the model nothing. Where you cut should match where the meaning ends.
BM25 by default
embeddings opt-in via /codeembed		 Searching code usually means searching for a name you already know. Building a meaning index takes minutes on a laptop; the word search takes milliseconds and usually wins anyway.
Its own output cap
smaller than every other tool's		 One search can return a lot. Cutting it shorter than a file read stops a single search from eating the entire turn.

The repo map: which files even matter?

A flat list of 300 filenames tells the model nothing. So we rank them, using the same idea Google originally used to rank web pages — applied to which file uses which.

The intuition

A file that many other files depend on is probably important — just as a web page that many pages link to probably matters. config.py scores high; a one-off script scores low.

Then: fit it to a budget

  • The map has to fit a size limit — but you can't know how many entries fit until you actually write them out.
  • So we guess, measure, halve the gap, repeat — about ten tries to land exactly on the limit. (The same trick as guessing a number between 1 and 1000.)
  • The ranking itself had to be rewritten — the obvious version re-checked every connection for every file, and made this the slowest tool we had.
The pattern behind all three chapters of RAG

Don't give the model more to read. Give it better ways to find what it needs.
A good search tool beats a bigger memory, and costs far less.

Custom #11 — sending a helper to do the reading

orchestration.py
Why

"Which file handles settings?" might take twenty file reads to answer. Do that in the main conversation and you have filled it with files that turned out not to matter — and every later turn re-sends them all.

What

A tool that starts a second assistant with its own private conversation and a limited set of abilities. It answers in a few lines. Its twenty file reads are thrown away with it.

How

Start a fresh assistant with its own instructions and tools, let it finish, and hand its final answer back as if it were any other tool result.

The trade in numbers

The helper reads 20 files → 40,000 words in its conversation.
The main assistant gets back about 15 lines.
The main conversation stays small because of how it is built, not because the model remembered to be careful.

Four roles, different tools

RoleToolsJob
orchestratorall + spawn_agentPlan the work, hand out jobs, check the result
explorerread-onlyLook around and report back. Physically cannot break anything
coderfullMake one specific change, then check it worked
reviewerread-onlyFind problems before we call it finished
Safety by simply not giving it the tool

The explorer has no way to write files at all. No clever wording in a file it reads can trick it into deleting something, because the ability isn't there.

Take the tool away. Don't ask the model nicely.

The same idea, scaled up: /audit

  • Reviewing a whole project doesn't fit in a local model's head. Not close.
  • So we split it up: review each small piece with a fresh helper, then merge all the findings into one report.
  • Each helper stays small and fast — the exact opposite of one giant request.
Generalisable

When a job doesn't fit, don't go looking for a bigger model — split the job.

Keeping the laptop cool

box 10 of 10 · red, left side
Why

A cloud tool never thinks about hardware. On your laptop, an hour of flat-out work means screaming fans — then the machine deliberately slows itself down to cool off. The longer you work, the worse it gets.

What

Two features no cloud tool has:
• a forced one-minute break after roughly ten minutes of solid work
• shorter replies and small pauses between turns

How

The break happens at the top of the loop, where nothing is half-finished. Both are on by default, and both switch themselves off when output is piped — so scripts and tests never sit there waiting.

Why the top of the loop

Pausing in the middle of a step would leave a request with no matching result sitting in the conversation — and most servers reject the whole thing when they see that.

The position isn't arbitrary — it makes breaking impossible, not just unlikely. Ctrl-C is handled at the same spot, for the same reason.

The bug that gentle mode caused

We capped how much the model could write, to keep the GPU cool. On a normal answer, hitting the cap just cuts off a sentence.

But when it writes a file, the file content travels inside the request itself. Cut that off and the request is incomplete — the model thought it had written the file, the user thought so too, and nothing reached the disk.

The fix, in three parts: the cap is now skipped entirely whenever tools are on the table; the default was raised 1,024 → 4,096; and anything still cut off is retried once with no cap at all.

And the twist: cutting off then retrying meant the model wrote the answer twice — which produced more heat than the cap ever saved.

The lesson

A limit you set for one reason will be hit by something you never thought about. Whenever you add a cap, ask what else travels down that path.

The honest reframe

We spent a long time trying to make it type faster. Typing speed was never the problem — it sat near 95 words a second throughout. The real pain was the waiting.

Nobody experiences "words per second". They experience "I pressed Enter, and then I waited." That is the number to improve.

Custom #13 — never trusting the model

Nine ways it knows to stop

A safety net that catches healthy behaviour is a bug

Our first version counted any bad request and shut down sessions that were working fine. A model that makes one good request and one bad one is still getting somewhere.

Now it only counts when everything in that round failed — and a single good request resets the count.

Treat the model like any untrusted input

  • It asks you first before writing, editing, or running anything.
  • Workspace confinement on the file tools (read / write / edit / glob / grep / repo_map) — paths resolving outside the launch directory are refused.
  • Your secrets are stripped out — commands it runs never inherit your API keys or cloud credentials.
  • Web fetching can't reach inside your network — private addresses are refused, and re-checked on every redirect, so it can't be talked into it halfway.
  • Undo checkpoints — files are snapshotted before every edit.
  • Small mistakes fix themselves — a wrong path is corrected and retried, a limited number of times.
--private: an enforced offline lockdown

Not a promise — an actual mechanism. The model address must be your own machine. Web fetching is removed entirely, so the model can't even ask. Commands run with the network blocked, and if that blocking isn't available, they refuse to run at all rather than run unprotected.

The most valuable bug we ever fixed

Our own docs said the tool couldn't write outside your project folder. For shell commands that was simply not true — it is a raw shell, with no path check in it at all. What actually protects you there is the confirmation prompt.

A safety claim that isn't true is worse than no claim, because people relax because of it. Say which mechanism enforces a guarantee — or don't make it.

Custom #14 — other people's tools, and testing without a GPU

mcp.py · providers.py

Plugging in tools we didn't write

Why

Our eleven tools can't cover everything. Other people have already built tools for databases, note vaults, ticket systems. MCP is an agreed way for any AI tool to talk to any of them, so nobody has to write a special connector each time.

What

741 lines, no new libraries. Each tool program is started as a small background process, and its abilities are added to the model's list next to our own.

How

Start it, ask what it can do, add those to the list. One that fails to start is skipped with a warning — it never takes the whole program down with it.

Never trust a server's own hints

A tool program can declare "this one is harmless, no need to ask". But a bad one could say that about something destructive, to get it run automatically.

So that claim is ignored unless you have said you trust that particular program. The decision to trust is always yours, never the tool's.

Also: names are checked so one program can't impersonate another, duplicates are skipped rather than silently overwriting, and a program that stops responding is shut down — so a late reply can never be mistaken for the answer to a different question.

The single best decision in this project

We never let the code call the model directly. It always goes through a swappable piece. That let us write a second one: a fake model that follows a script.

Why this matters more than it sounds

Nearly every bug here is a loop bug: a request with no matching result, a counter that never resets, messages added in the wrong order.

You cannot chase those with a real model — it gives a different answer every time, and slowly. Against a script they become ordinary tests that run in milliseconds.

Adding this swappable piece later, once twelve different places all call the model directly, is miserable work. Done at the start, it costs ten minutes.
