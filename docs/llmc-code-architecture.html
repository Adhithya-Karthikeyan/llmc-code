01

The problem we are solving

why this exists

You can download a good model today. You still can't use it.

LM Studio will happily run a 30-billion-parameter coding model on your laptop. What you get is a chat box. What you wanted is something that reads your repo, edits files, runs your tests and fixes what broke.

The gap

A model can only turn text into text. It cannot open a file, run a command, remember yesterday, or stop itself when it is confused.
Something has to sit between the model and your computer. That something is a harness, and building one is what this deck is about.

Why not just use the cloud tools?

  • Privacy — your source code never leaves the machine.
  • Cost — no per-token bill, no rate limits.
  • It works offline — on a plane, in a lab, behind an air gap.
But local changes everything

A cloud harness can assume a big, fast, well-behaved model. We can assume none of that. Every custom piece in the second half of this deck exists because of that one difference.

Four constraints — and what each one forced us to build

ConstraintWhat we had to build
Small, messy models

One laptop GPU

In one line

A harness for running LLMs locally = the loop, the tools, and everything needed to make a small model on modest hardware behave like a useful engineer.

03

What happens when you press Enter

data flow
Why a loop

One question-and-answer round cannot fix a bug. The model must look, act, see what happened, then act again. Each pass it knows strictly more than the last.

What ends it

A reply with no tool calls. Plain words mean the model has nothing left to look up — so its words are the answer. The text is buffered, then rendered once as markdown, so headings and code fences display properly instead of as literal ##.

How it stays safe

A hard iteration cap (80), plus eight more guards. Writes and shell commands ask you first; reads just run.

The whole agent, in 20 lines

the loop

Strip away 3,000 lines of production hardening and Agent.run() is this. This is a real, working agent — tested with a scripted fake model.

the core of every coding agent ever written
def agent(task, max_steps=12):
    messages = [{"role":"system", "content": SYSTEM},
                {"role":"user",   "content": task}]

    for _ in range(max_steps):              # the iteration guard
        reply = client.chat.completions.create(
            model=MODEL, messages=messages, tools=SCHEMA
        ).choices[0].message
        messages.append(reply.model_dump(exclude_none=True))

        if not reply.tool_calls:            # plain words = DONE
            return reply.content

        for call in reply.tool_calls:
            args = json.loads(call.function.arguments)
            if call.function.name in NEEDS_OK and not ask_user():
                out = "DENIED by the user."
            else:
                try:
                    out = TOOLS[call.function.name](**args)
                except Exception as e:      # errors are DATA
                    out = f"ERROR: {type(e).__name__}: {e}"
            messages.append({"role":"tool",
                             "tool_call_id": call.id,
                             "content": str(out)[:4000]})   # ALWAYS cap

    return "Stopped: hit the step limit."

Five decisions hide in those lines

The lineWhy it matters
str(out)[:4000]An uncapped result poisons the context forever. Cap at the source.
except → "ERROR: …"A tool must never raise. The error is fed back so the model can correct itself.
range(max_steps)Without it, one confused model loops all night.
NEEDS_OKThe human stays in the loop for anything destructive.
The system promptBehaviour is configured in English. "Explore before you answer" changes everything.
The error rule is the big one

Compare two tool errors:
• "error" → the model guesses, and death-spirals.
• "path not found; did you mean llmcode/agent.py?" → fixed next turn.
Error messages are prompts. Write them for the model, not for a log file.

Tools — giving the model hands

tools.py

A tool is three things

llmcode/tools.py — the Tool dataclass
Tool(
    name="read_file",
    description="Read a text file. Use before answering about code.",
    parameters={"type":"object", "required":["path"],   # JSON Schema →
                "properties":{"path":{"type":"string"},   # sent to the model
                              "offset":{"type":"integer"},
                              "limit":{"type":"integer"}}},
    fn=_read_file,                       # the Python that runs
    requires_confirmation=False,         # reads are safe
)

1. a schema (documentation for the model) · 2. a Python function · 3. a safety flag.

Tool results have ONE shape

{"ok": true, "result": …} or {"ok": false, "error": …}. They never raise. A crash would end the turn; an error just teaches the model.

Schema wording is prompt engineering

"Read a file" gets you whole-file reads. "Read a file — use offset/limit for big files" gets you slices. Same code, different behaviour.

The eleven tools

Two real safety bugs we fixed

• The docs claimed writes were "workspace-confined" — they weren't. A false security claim is worse than none.
• write_file corrupted files whose content contained tool-call markup. The parser swallowed the next call.

Custom #1 — every model speaks a different language

providers.py
Why

Cloud models are served with one strict tool-call format. Local models come from a dozen labs, each with its own chat template. Many do not emit native tool calls at all — they print the call as ordinary text and expect the client to notice.

What

A parsing layer that recognises one native format plus six text dialects — DeepSeek, Qwen/Hermes, Mistral, Llama (two spellings), Qwen-XML, and a fenced-JSON protocol we invented for models that support nothing.

How

Detect the dialect by its marker → extract name and body → coerce to a Python dict. Everything downstream sees one shape and never learns a dialect existed.

The bug that forced this

write_file failed for weeks with "requires a string 'path'". Two stacked causes: qwen emitted XML parameters, not JSON, so the native arguments field arrived empty — and it used Claude's parameter names.

The hard part: where does a value end?

Models often open <parameter=content>, dump an entire Python file, and never close the tag. So a value must end at whichever terminator comes first. Overshoot and you write the next tool call's markup into the user's source file. That is exactly the write-corruption bug we fixed.

Custom #2 — wrong argument names, and refusing to guess

tools.py

Even once the call is extracted, the names may be wrong. Local models are trained on Claude's and OpenAI's docs, so they call our path parameter file_path, and our old parameter old_string.

llmcode/tools.py — the alias table (excerpt)
_ARG_ALIASES = {
  "read_file": {
     "path": ("file_path", "filepath", "filename", "file", "target_file")},
  "write_file": {
     "path": ("file_path", "filepath", …),
     # NOTE: deliberately NO new_string/new_str here — those are edit_file's
     # `new` key; mapping them to write_file content would turn a mis-targeted
     # edit into a DESTRUCTIVE whole-file overwrite with just the fragment.
     "content": ("file_text", "text", "body", "data", "code")},
  "edit_file": {
     "old": ("old_string", "old_str", "search", "find"),
     "new": ("new_string", "new_str", "replace")},
}
Read that comment again

An alias table is a guessing machine. The author deliberately left out a plausible alias because the failure mode was destructive. Knowing which guess not to make is the whole skill.

The rule that makes aliasing safe

for canonical, syns in aliases.items():
    cur = args.get(canonical)
    if cur not in (None, ""):
        continue      # model gave a real value — authoritative
    if cur == "":
        continue      # explicit empty — intentional, keep it
    for syn in syns:    # else backfill from the first alias present
        …
  • An alias may only fill a blank — never overrule what the model actually said.
  • Explicit empty wins. content: "" means "create an empty file".
  • Copy-on-write — so the confirmation prompt you saw and the arguments that ran can never drift apart.

And two places we deliberately stop

SituationWhat we do
Two tool-shaped blocks in one replyRefuse to run any. Executing only the first silently drops the rest — the model would never learn its second instruction vanished.
A block inside prose or a <think> sectionIgnore it. Otherwise the model explaining rm -rf would actually run it.
The transferable rule

Be liberal in what you accept, strict in what you execute. A missed call costs one turn. A wrong call costs your source file.

Custom #3 — why long chats kill a local model

context management
Why

Every turn re-sends the entire conversation. Answering has two phases: prefill (read the whole prompt — cost grows with length) and decode (write the reply — roughly constant). On a laptop GPU, prefill is where the time goes.

What

A per-message context budget, plus machinery to keep history under it — so the model sees what this message needs, and nothing else.

How

Four levers, cheapest first: measure → budget → trim → compact.

Analogy

A colleague with total amnesia between sentences. To answer, they must re-read the entire meeting transcript — every time. Decode speed is how fast they talk. Prefill is how long they sit re-reading. Fifty pages of stale notes doesn't slow their speech; it makes them silent for two minutes first.

The measurement that started this work

A user typed "what happened?" — four words. The program sent 55,000 tokens of stale history. The reply took ~20 minutes.

Auditing showed tool outputs were 56% of the history; counting file content stored inside past write_file calls, over 90%.

The four levers

LeverWhat it doesCost

The request classifier deliberately errs upward: when unsure, treat it as a real task. Misjudging a task as trivial breaks the answer; misjudging trivia as a task just wastes a little time.

Custom #4 — trimming and compaction

agent.py
trim — free, every turn

Old tool results cut to 500 chars; file content inside old tool calls cut to 160.
Three invariants: idempotent (a marker stops it re-cutting its own note), structure-preserving (ids stay paired), actionable (the note says how to get the rest back).

compact — costs a model call

The model summarises old turns into one note: decisions, files touched, open tasks. Not truncation — deleting messages loses the decisions inside them.

compaction can backfire

A weak model sometimes writes a summary as long as the original. So: snapshot first, require a ≥3% saving, otherwise roll back and don't retry until history grows 10%. Rewriting history also costs the prompt cache — see the next slide.

Custom #5 — CAG: free speed from doing nothing

cache-augmented generation
Why

The server keeps a KV cache: state for tokens it already read. If your next request starts with the byte-identical prefix, prefill for all of it is skipped — most of your waiting time, for free.

What

One rule, enforced everywhere: history is append-only. Never insert, never reorder, never rewrite the front.
RAG makes prompts smarter; CAG makes them cheaper.

How

Anything dynamic — recalled memories, per-turn hints — is appended to a copy of the list, at the very end, on the first call only. It rides the uncached tail, which costs nothing.

The same discipline, three more places

• Text-only messages keep content a plain string (attaching an image makes it a list — a different prefix).
• Tool schemas are memoised, so key order can't drift.
• A useless compaction is rolled back — the code would rather carry extra tokens than break the cache.

Why the recall note is never stored

Keeping it out of self.messages wins three times: the prefix stays cacheable, it is never written to the session file (so it can't leak), and compaction can never mangle it — because it was never there.

Custom #6 — RAG: remembering without re-reading

memory.py
Why

The last slide said: send less history. But some of it matters — "we decided to use BM25 by default". Drop it and the agent is forgetful; keep it all and it is slow.

What

Put everything in a store, search it with the current question, and put only the few matching pieces in the prompt. That is RAG — retrieval-augmented generation.

How

Two search engines, both hand-written: BM25 for exact words, embeddings for meaning. Results are fused and injected as one ephemeral note.

Where it lives

A plain .memory.json per project, vectors in a binary sidecar. Record tokenisation is cached across turns, and a corpus-wide index is built once — otherwise every query would re-tokenise the whole store.

Retrieval runs ONCE per turn

Before the loop, never inside it. Searching is expensive; doing it on every tool round would undo the speed it buys. And it is skipped entirely for a trivial message.

Failure is always swallowed

except Exception: records = []. Memory is an enhancement. Losing it must never cost you the turn.

Custom #7 — BM25, written by hand

keyword search
llmcode/memory.py — the entire scoring loop
for term in q_terms:
    f = tf.get(term, 0)          # times the term is in THIS doc
    if f == 0: continue
    n_q   = df[term]              # how many docs have it at all
    idf   = math.log(1 + (n - n_q + .5) / (n_q + .5))   # rarity
    denom = f + k1 * (1 - b + b * (dl / avgdl))     # length
    s    += idf * (f * (k1 + 1)) / denom          # saturating

Why not just count shared words? Because every document contains "the". BM25 is the classic fix, and it still beats fancier methods on code, where exact identifiers matter more than vibes. Two knobs: k1=1.5, b=0.75.

The stopword list is load-bearing

Dropping "the"/"and"/"is" looks cosmetic. It isn't: a stopword-only overlap would leave a non-zero BM25 score, so the next slide's gate would never escalate to embeddings — the exact case it exists for. Removing them makes "score is zero" mean "no real overlap".

Don't copy a stopword list off the internet

Ours deliberately keeps on, off, no, not — in a CLI those are data (/mcp on|off), not filler. A generic list would have silently deleted them.

Custom #8 — embeddings, and when not to use them

the hybrid gate
What an embedding is

A piece of text turned into 768 numbers — a point in space where texts about similar things land near each other. "where do my settings live?" lands near "the config file is in ~/.llmcode" even though they share no words.

To compare two points we measure the angle, not the distance — length just reflects how wordy the text was. That is cosine similarity, and it is 12 lines:

llmcode/memory.py — cosine()
dot = na = nb = 0.0
for x, y in zip(a, b):
    dot += x * y      # how much they point the same way
    na  += x * x
    nb  += y * y
if na <= 0.0 or nb <= 0.0: return 0.0
return dot / math.sqrt(na * nb)     # 1.0 = identical meaning
Note what the docstring promises

Never raises, never NaNs. It returns 0.0 for garbage input — which is exactly the right answer, and stops one corrupt record taking down a turn.

The decision that made it fast

Running both engines every query means an embedding round-trip every turn — which on a single GPU may force a model swap. So:

llmcode/memory.py — the whole policy, in one condition
best_bm25 = bm25_full[0][1] if bm25_full else 0.0
if provider is not None and (
    mode == "embed" or (mode == "auto" and best_bm25 <= 0.0)
):
    embed_idx = self._embed_rank(query, provider, pool_k)

Custom #9 — a vector database in 200 lines

no Chroma, no FAISS, no NumPy
Why

Embeddings must survive a restart. A real vector DB means a new dependency, often a server process — absurd for a personal CLI holding a few thousand vectors on one machine.

What

A dict of array('f') in RAM, a JSON file for metadata, and a packed float32 sidecar for the numbers. Search is a for loop over cosine similarity.

How

array('f') stores 4 bytes per number instead of a boxed Python float (~32 B + pointer). Writing them as raw bytes avoids turning every float into a decimal string in JSON.

When this is the right answer

Thousands of vectors, one machine, one user. A loop over 4,000 cosines is milliseconds. You need a real vector DB at millions of vectors, or when many processes share one index — not before.

The lesson that generalises

Whenever two files must agree, one of them has to prove it matches the other. A checksum in the metadata is the cheapest proof there is — and it is the difference between "re-embed on next launch" and "silently wrong answers forever".

Custom #10 — searching the codebase itself

code_index.py · repo_graph.py
Why

A small model cannot read a 50-file repo. Reading three files already costs more context than it has. It needs to find the right 40 lines, not read everything.

What

code_search — a tool the model calls itself, backed by the same hybrid engine as memory, plus repo_map, a compact structural index of the project.

How

Chunk by function and class, not by fixed line count, so every hit is a complete, self-contained unit. Index once, cache it, cap the output.

Three deliberate choices

ChoiceReason
AST-aware chunkingA hit that starts mid-function teaches the model nothing. Chunk boundaries should be meaning boundaries.
BM25 by default
embeddings opt-in via /codeembed		 Code search is usually an identifier search. Indexing a repo with embeddings costs minutes on a laptop; BM25 costs milliseconds and usually wins.
Its own output cap
smaller than every other tool's		 One search can return many chunks. Capping it harder than read_file keeps a single call from eating the turn's whole budget.

The repo map: which files even matter?

Showing the model a flat list of 300 files is useless. We rank them — with PageRank, Google's original link-ranking algorithm, run over your import graph.

The intuition

A file imported by many other files is structurally important, exactly as a web page linked by many pages was important. config.py scores high; a one-off script scores low.

Then: fit it to a budget

  • The map must fit a token budget, but you don't know how many entries fit until you render them.
  • So: binary-search the entry count — render, estimate tokens (chars // 4), adjust, repeat. About 10 tries to land exactly at the budget.
  • PageRank itself was rewritten to O(N+E) — the naive version re-scanned all edges per node and made repo_map the slowest tool in the set.
The pattern behind all three chapters of RAG

Don't give the model more context — give it better tools for finding context. A good search tool is worth more than a bigger context window, and it is a lot cheaper.

Custom #11 — sub-agents: context isolation

orchestration.py
Why

"Which module handles config?" might need twenty file reads. Do them in the main conversation and you have burned the context window on files that turned out to be irrelevant — and every later turn re-sends them.

What

spawn_agent — a tool that starts a fresh agent with its own private conversation, a restricted toolset, and a role prompt. It returns a short summary. Its twenty file reads are thrown away with it.

How

Build a new Agent with the role's system prompt and tool subset, run it to completion, return its final text as the tool result.

The economics

Sub-agent reads 20 files → 40,000 tokens in its context.
Parent receives ~15 lines.
The parent's context is protected by construction, not by discipline.

Four roles, different tools

RoleToolsJob
orchestratorall + spawn_agentPlan, delegate, validate
explorerread-onlyInvestigate and report. Cannot damage anything by construction
coderfullImplement one scoped change, then validate it
reviewerread-onlyCritique before it's called done
Security through scoping

An explorer has no write tools in its registry. It cannot be prompt-injected into deleting a file, because the capability isn't there. Scope tools by role, not by asking the model nicely.

The same idea, scaled up: /audit

  • Reviewing a whole repo doesn't fit in any local context window.
  • So map-reduce it: split the repo into chunks, review each in a fresh isolated context, then merge the findings.
  • Each worker stays small and fast — the exact opposite of one giant prompt.
Generalisable

When a job doesn't fit in context, don't buy a bigger context — partition the job.

Custom #12 — your laptop is not a datacenter

cooldown.py · gentle mode
Why

A cloud agent never thinks about hardware. An agent on your laptop runs the GPU flat out for an hour, the fans scream, and the machine thermally throttles — so it gets slower the longer you work.

What

Two features that exist in no cloud agent:
• Cooldown — a forced ~1-minute break after every ~10 minutes of continuous work.
• Gentle mode — a cap on output tokens plus pacing between turns.

How

Cooldown is checked at the top of the agent loop — a safe checkpoint where nothing is half-written. Both are on by default and disable themselves when output isn't a terminal, so scripts and tests never pause.

Why the top of the loop

Pausing mid-turn would leave an assistant(tool_calls) message with no matching results — which most servers reject outright. Position isn't arbitrary; it is chosen so the invariant cannot break. The same reasoning places the Ctrl-C check.

The bug that gentle mode caused

The output cap (1,024 tokens) was meant to keep the GPU cool. For a chat answer, hitting it just truncates some prose.

For write_file it was silent data loss — the whole file content travels inside the tool call's JSON arguments. Truncated arguments meant the model believed it wrote the file, the user believed it too, and nothing landed on disk.

The fix, in three parts: the cap is skipped entirely on any turn that offers tools (gentle_for_this_call = gentle_mode and not tools); the default rose 1,024 → 4,096; and a generation that still stops on the cap is retried once uncapped.

The second-order lesson: truncate-then-retry meant two generations — more heat than the cap ever saved. On tool turns, pacing is the heat lever now, not the cap.

The lesson

A limit you set for one reason will be hit by something you never considered. Whenever you add a cap, ask: what else travels through this path?

The honest reframe

We chased tok/s for a long time. Decode speed was never the problem — it sat near 95 tok/s throughout. The pain was wall-clock: heavy defaults and huge prompts.

Measure the thing the user feels

The user does not experience tok/s. They experience "I pressed Enter and waited". Optimise that number.

Custom #13 — never trusting the model

guards · safety · privacy

Nine guards, because the loop must always end

GuardBound
Iteration cap80 passes
All-parse-errors circuit breaker3 bad batches
Identical-batch loop guard4 repeats
Empty-turn nudge (thought, said nothing)2 retries
Truncation retry (cap ate a write)once per pass
Constrained-decode retry (bad JSON args) · markup nudgeonce each
Cancel check (Ctrl-C can't corrupt history)every pass
Read-budget nudge (read less, search more)once per turn
A guard that catches healthy behaviour is a bug

The first circuit breaker counted any parse error and killed working sessions. A model that emits one good call and one malformed call is still making progress. It now only counts when the whole batch failed — and one good call resets it.

Safety: the model is untrusted input

  • Confirmation gates on every write, edit and shell command.
  • Workspace confinement on the file tools (read / write / edit / glob / grep / repo_map) — paths resolving outside the launch directory are refused.
  • Secret scrubbing — child processes get an allowlisted env; API keys, AWS_*, GITHUB_TOKEN are never inherited.
  • SSRF guard on web_fetch — loopback, private and cloud-metadata IPs refused; connection pinned to the validated IP; re-checked on every redirect.
  • Undo checkpoints — files are snapshotted before every edit.
  • Self-healing — a failed tool call is auto-corrected and retried, bounded.
--private: an enforced offline lockdown

Not a promise — a mechanism. The model URL must be loopback and is IP-pinned; web_fetch is removed from the toolset; run_bash runs in a no-network sandbox and fails closed if it is unavailable; the HTTP client uses trust_env=False so proxy variables cannot tunnel traffic out.

The most valuable bug we ever fixed

The docs claimed writes were "workspace-confined". For run_bash that was false — it is a raw shell, and there is no path check in it at all. Its real boundary is the confirmation gate plus the scrubbed environment.

A false claim is worse than none — people relax because of it. Name the mechanism that enforces a guarantee, or don't claim it.

Custom #14 — MCP, and testing without a GPU

mcp.py · providers.py

MCP — plugging in other people's tools

Why

Our eleven tools cannot cover everything. Model Context Protocol is a standard way for any AI client to talk to any tool server — a filesystem server, a database server, a notes vault — without us writing an integration for each.

What

A 741-line, stdlib-only JSON-RPC 2.0 client over stdio. No SDK, no new dependency. Servers are child processes; their tools are merged into the model's tool list as mcp__<server>__<tool>.

How

Spawn → handshake (initialize → tools/list) → merge. A server that fails to start is skipped with a warning, never crashes the CLI.

Never trust a server's own hints

MCP lets a server mark a tool readOnlyHint. A malicious server could mark a destructive tool read-only to auto-run it. So the hint only relaxes the confirmation gate when you opt in per server. The trust decision is the operator's, never the server's.

Also hardened: tool names validated (no namespace forging), duplicate names skipped rather than overwritten, per-call timeouts, and a timed-out connection treated as poisoned — the child is killed so a late reply can't corrupt a later call.

The best engineering decision in the project

The provider is an interface, not a class that calls an API. That let us write a second implementation: MockProvider — a scripted, deterministic fake model.

Why this matters more than it sounds

Agent bugs are loop bugs: a dangling tool id, a guard that never resets, history appended in the wrong order. You cannot debug those against a real model — it is non-deterministic and slow. Against a script, they are unit tests that run in milliseconds.

Build this seam on day one

Retrofitting a provider interface into a codebase that calls the API directly from twelve places is miserable. It is ten minutes of work up front.

If you remember one thing

The model is not the program. About 95% of this codebase is the machinery around it — and that machinery is where the quality comes from.
